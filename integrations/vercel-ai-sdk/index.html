sipi.bot + Vercel AI SDK

Use sipi.bot as middleware in the Vercel AI SDK. Every generateText, streamText, and generateObject call is intercepted and policy-checked.

Middleware is the right seam

The AI SDK gives you a model-level extension point, which is a better place for a spend check than wrapping every call site. Wrap the model once with middleware and every generateText, streamText and generateObject that uses it inherits the policy — including the calls a colleague adds next month without reading this page.

import { wrapLanguageModel } from "ai";

const spendFirewall = {
  async wrapGenerate({ doGenerate, params }) {
    const res = await fetch(
      "https://sipi.bot/v1/transactions/evaluate", {
        method: "POST",
        headers: { "Content-Type": "application/json",
                   Authorization: `Bearer ${process.env.SIPI_KEY}` },
        body: JSON.stringify({
          amount: estimateUsd(params),
          merchant: "model-provider",
          category: "llm",
          description: "ai-sdk generate",
        }),
      });
    const d = await res.json();
    if (d.decision !== "APPROVED") throw new Error(`${d.decision}: ${d.reason}`);
    return doGenerate();
  },
};

const model = wrapLanguageModel({ model: baseModel, middleware: spendFirewall });

Implement the streaming path as well as the generate path. Anything you leave unwrapped is simply unguarded, and streaming is usually the one that ships first.

Why a local counter cannot hold a daily budget

This is the part that specifically bites on serverless, and it catches good engineers. An in-memory total works perfectly in development, where one long-lived process sees every request. In production your handler runs across many isolated invocations. Each one starts with its own memory, so each one starts the day's counting from zero.

A module-scoped let spentToday = 0 does not enforce a daily ceiling in a serverless deployment. It enforces a per-instance ceiling, silently, and the number of instances is not yours to control.

Any ceiling that spans requests has to live in shared state. That is the main structural reason to use an external policy service here rather than a few lines of local arithmetic — not because the arithmetic is hard, but because there is nowhere local to keep it.

Streaming forces the decision earlier

Tokens that have been streamed to a user are billed and cannot be recalled. The decision therefore has to happen before the stream opens, using an estimate, and there is no second chance to reconsider halfway through. Price the worst case from your token ceiling — for streaming the worst case is the only figure that protects you.

Rules that fit an edge deployment

Rule typeWhat it does on this integration
daily_totalThe rule that most needs shared state, and the one a serverless app cannot enforce for itself.
velocityBounds a burst across invocations — including one triggered by traffic rather than by a bug.
per_transactionCaps a single oversized generation before the stream opens.
approval_thresholdBetter suited to background jobs than to a user-facing route, where nobody is waiting to approve.

Limits

  • The check costs a network round trip on a latency-sensitive path. On user-facing streaming routes, measure it before assuming it is free.
  • It prices your estimate. Reconcile against real usage after the response completes, or the daily total drifts from reality.
  • Model calls that bypass the wrapped model instance are not covered. Wrap once, centrally, and export that instance rather than the raw one.

Questions

Does this work on the edge runtime?

Yes — it is a standard fetch to an HTTPS endpoint, with no Node-only APIs involved.

What should a user see when a call is blocked?

Something honest and specific. A blocked request is a budget decision, not an outage, and "this request exceeds the configured budget" is far more useful than a generic failure — for the user and for whoever debugs it later.

Can I set different budgets per route?

Give each route its own agent identity and key. A background job and an interactive chat route should not share a ceiling.
