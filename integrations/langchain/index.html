sipi.bot + LangChain

Add sipi.bot as a callback handler in LangChain. Every tool call and LLM invocation is policy-checked against your agent's spend rules.

Callbacks are the natural hook, with one caveat

LangChain already runs a callback on every LLM invocation and every tool start, which is exactly where a spend decision belongs. You do not need to wrap each model client individually — implement BaseCallbackHandler once and pass it to the chain.

The caveat is that a callback has no return channel. There is no value you can return that means "deny". The only way to stop the call is to raise, and the exception surfaces as a chain failure that your calling code has to handle deliberately. Plan for that rather than discovering it in production.

from langchain_core.callbacks import BaseCallbackHandler
import requests

class SpendFirewall(BaseCallbackHandler):
    def on_llm_start(self, serialized, prompts, **kw):
        self._check(estimate_usd(serialized, prompts), "llm",
                    serialized.get("name", "model"))

    def on_tool_start(self, serialized, input_str, **kw):
        self._check(tool_cost(serialized), "tool",
                    serialized.get("name", "tool"))

    def _check(self, amount, category, name):
        d = requests.post(
            "https://sipi.bot/v1/transactions/evaluate",
            headers={"Authorization": f"Bearer {SIPI_KEY}"},
            json={"amount": amount, "merchant": name,
                  "category": category, "description": f"langchain {category}"},
            timeout=5,
        ).json()
        if d["decision"] != "APPROVED":
            raise SpendBlocked(f"{d['decision']}: {d['reason']}")

Tools cost money too, and they are the part people forget

Attention goes to token spend because that is what the pricing page talks about. But a LangChain agent's tools are where the genuinely uncapped spend usually lives: a paid search API, a data vendor, a scraping service, anything that provisions infrastructure. These are billed per request, they are invoked in a loop, and none of them appear on your model provider's invoice.

Handling on_tool_start alongside on_llm_start is what makes the coverage real. Give tools their own category so you can see the split.

A useful diagnostic: run for a day, then compare tool spend to model spend in the audit trail. Teams are routinely wrong about the ratio, usually in the direction of underestimating tools.

max_iterations bounds steps, not dollars

LangChain's own iteration limit is a good reflex and an incomplete control. Ten iterations of a cheap tool and ten iterations that each carry a large context cost wildly different amounts, and the limit cannot tell them apart. It bounds how long an agent runs. It does not bound what running costs.

Rule typeWhat it does on this integration
velocityCatches the agent that loops within its iteration budget but fires far more calls than the task warrants.
category_limitSeparates tool spend from model spend — the split that makes LangChain cost legible.
daily_totalThe aggregate ceiling across every chain sharing the key.
merchant_allowGenuinely useful here, because a LangChain agent's tools reach many third parties rather than one provider.

Where this does not reach

  • Anything that bypasses the callback. A tool that spends inside its own implementation, without going through a registered tool interface, is invisible.
  • Streaming responses already in flight — the decision happens at start, and after that the tokens are committed.
  • Cost you have not modelled. tool_cost is yours to write; the firewall enforces the number, it does not discover it.

Questions

Does this work with LangGraph?

The same handler applies, since the callback interface is shared. Graphs make the per-node attribution more useful — send the node name as the description and the audit trail tells you which step in the graph is expensive.

What about async chains?

Implement the async callback methods and use an async HTTP client, so the check does not block the event loop on every invocation.
