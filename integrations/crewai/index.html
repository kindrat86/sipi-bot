sipi.bot + CrewAI

CrewAI agents that execute tasks with spend consequences need per-agent velocity caps. sipi.bot enforces them per crew member.

Delegation multiplies calls you did not write

A CrewAI crew is easy to reason about at the task level and harder to reason about at the invocation level. One task assigned to one agent is rarely one model call: the agent reasons, calls a tool, reads the result, reasons again. Add delegation and a task can fan out into work you never explicitly requested.

The hierarchical process makes this sharper. A manager agent coordinates the crew, and the manager is itself an LLM — every coordination decision is a billed call that appears nowhere in your task list. Crews often cost meaningfully more under hierarchical process than sequential, for structural reasons rather than because anything went wrong.

Budget per crew member, not per crew

A single ceiling for the whole crew tells you that something is expensive. A ceiling per agent tells you which role is expensive — and roles differ enormously. A researcher that searches and reads costs very differently from a writer that produces one long output, and averaging them hides both.

import requests
from crewai import Agent, Crew, Task

def guarded_tool(fn, role, cost, sipi_key):
    def wrapper(*a, **kw):
        d = requests.post(
            "https://sipi.bot/v1/transactions/evaluate",
            headers={"Authorization": f"Bearer {sipi_key}"},
            json={"amount": cost, "merchant": fn.__name__,
                  "category": "tool", "description": f"{role} -> {fn.__name__}"},
            timeout=5,
        ).json()
        if d["decision"] == "BLOCKED":
            return f"Budget exceeded for {role}: {d['reason']}"
        return fn(*a, **kw)
    return wrapper

Returning the block as a tool result rather than raising is often the better move in CrewAI. The agent reads it, understands the tool is unavailable, and writes up what it has — instead of the task dying mid-crew.

Retries are where task cost hides

When a task's output fails validation, the framework's instinct is to try again. That is usually the right behaviour and it is billed every time. A task that retries three times costs roughly four times its nominal price, and nothing in the run summary draws attention to it. A velocity rule catches this shape early, because retries cluster tightly in time.

Rule selection for crews

Rule typeWhat it does on this integration
velocityCatches retry loops and over-eager delegation, both of which burst rather than accumulate slowly.
category_limitSplits tool spend from model spend — essential when crew members use paid search or data APIs.
daily_totalThe crew-wide aggregate, applied per agent identity for attribution.
merchant_allowConstrains which third-party tools a crew member may spend on at all.

Honest limits

  • Spend inside the framework's own coordination — manager reasoning under the hierarchical process — only counts if you route it through the check like any other call.
  • The firewall does not evaluate output quality, so it cannot tell a productive retry from a doomed one.
  • Per-agent attribution depends on you issuing per-agent keys. One shared key gives you one shared number.

Questions

Sequential or hierarchical — does it change the policy?

It changes the numbers, not the structure. Hierarchical adds manager calls, so the same crew needs more headroom under the same rules. Measure both before setting the ceiling.

Can one agent's block stop the crew?

Only if you let it propagate. Returning the block as a tool result keeps the crew running with one member constrained, which is usually what you want.
